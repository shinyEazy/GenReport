Pattern 1: Predominantly Categorical, Text-Based Design

The schema is overwhelmingly Text-type (87.5%) with only 2 Integer fields (Value_Denominator and Value_Numerator). This design choice serves several purposes:

  • Flexibility: The Value field accommodates diverse formats—flags, integers, decimals, percentages, and textual descriptions—all stored uniformly as Text.
  • Cross-domain compatibility: Different clinical metrics (survival rates, wait times, treatment percentages) can share the same data structure.
  • Percentage transparency: By keeping Numerator and Denominator as separate Integer fields alongside the computed Text-based Percentage, the schema enables independent verification of all calculated values.

💡 Design Insight: The schema follows a "wide schema" pattern common in UK NHS open data—embedding metadata (organisation, timing, classification) directly alongside measurements rather than joining multiple tables. This makes individual rows self-contained and easier to publish.

Pattern 2: Sophisticated Time Architecture with 8 Variants

The WhenOccurred field is one of the most complex aspects of this schema, supporting 8 distinct temporal classifications:

Audit Period Multi-year aggregated events spanning a range Treatment rates aggregated from 2009-10 to 2018-19
Audit Year offset -6 months One-year window starting 6 months before audit year Follow-up data starting September of preceding year
Audit Year offset -12 weeks Recent quarter prior to audit year cutoff Q4 data before the March financial year end
Audit Year offset -30 days One month before audit year ends Last month of activity before April cutoff

Days since diagnosis Relative time from patient diagnosis Survival analysis: outcomes at day 30, 90, 365
Years since diagnosis Longitudinal follow-up intervals 5-year survival rate, 10-year progression
⏱️ Key Rule: An audit year runs from March to April. This means "2018–19 Audit Year" covers roughly 1 April 2018 through 31 March 2019—not calendar year dates. All five guidance examples in the specification are designed to help data consumers correctly interpret this convention.

Why This Complexity?

Prostate health auditing involves multiple temporal perspectives:

  • Operational metrics (waiting times, throughput) use narrow windows like "Audit Year offset -30 days"
  • Trends over time require multi-year spans like "Audit Period" combining several fiscal years
  • Clinical outcomes such as survival rates depend entirely on patient-specific timelines ("Days/Years since diagnosis")

This flexibility allows a single schema to serve both operational auditing and clinical research use cases.

Pattern 3: Rich Measurement System with 12 DataType Options

The DataType field is critical—it tells any consumer how to parse and interpret the Value field. There are 12 distinct measurement types defined:

📊 Simple Value Types (5)

  • Flag — Binary yes/no indicator
  • n — Whole number count
  • n.n — Decimal number (single precision)
  • % — Percentage value
  • Text — Free-form string

📈 Week Statistics (7)

  • Weeks: Average — Mean waiting/wait time
  • Weeks: Minimum — Shortest interval
  • Weeks: Lower quartile — 25th percentile
  • Weeks: Median — 50th percentile (p50)
  • Weeks: Upper quartile — 75th percentile
  • Weeks: Maximum (capped) — Max capped at 1.5×IQR above UQ
  • Weeks: Out of range — Flagged outliers (>1.5×IQR above UQ)
📏 Statistical Rigor: The week statistics implement proper outlier detection using the Interquartile Range (IQR) method. Values exceeding Q3 + 1.5×IQR are flagged separately as "Out of range" while also appearing in a capped "Maximum" field. This dual-reporting prevents extreme outliers from skewing visualizations while preserving data integrity.

Pattern 6: Four-Way Section Classification

The Section field segments all data into four categories, each serving a different purpose in the annual report:

Section Purpose Typical Content
National Standard Mandatory compliance indicators Wait times, survival rates, referral targets
National Standard Summary Aggregated overview of standards performance Summary tables, pass/fail counts by region
Reference Tables Detailed breakdowns for deeper analysis Centre-level detail, trend data by year

This classification matters because it determines which DataType values are applicable—survival analysis uses different formats (percentages derived from Kaplan-Meier curves) compared to standard operational metrics.

Recommendations for Data Users

✅ Recommended Approaches

  • Parse numerically first: Convert Value to numeric where DataType ∈ {n, n.n, %}, treating Text values separately
  • Leverage numerator/denominator: Recalculate percentages independently to verify reported values
  • Group by Section: Apply different parsing rules per Section (survival vs. operational metrics)
  • Respect audit year boundaries: Never assume calendar year alignment
  • Handle outlier flagging: Use the separate "Weeks: Out of range" count when computing averages

⚠️ Watch Outs

  • Coding issues: File requires Latin-1 encoding (contains en-dashes)
  • Missing context: Without the companion data files, this schema is purely structural
  • Kaplan-Meier exception: Some percentages don't have numerator/denominator available
  • Offset semantics: Understand whether "-6 months" refers to start-of-window or end-of-window
  • Version awareness: This is specifically the 10th edition; field definitions may change across editions
